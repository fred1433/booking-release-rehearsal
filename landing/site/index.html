Paperclip booking-release rehearsal

Independent demonstration using synthetic data. No access to any client's code or Paperclip instance. Payments are not connected.

One small change to a private-session booking app, taken through a real Paperclip instance and a protected release on 14 October 2026: a double-booking defect planted on purpose, fixed by one agent, reviewed by another, approved through the operator account, released, rolled back and released again. Every step below links to its record.

The operator role (Paperclip approvals, GitHub environment approvals and merges) was played by the build session through the operator account; no person reviewed these changes.

This frame is the production release itself, not a mock-up. A synthetic teacher in Paris, a learner in Sydney, sessions of 30, 45 or 60 minutes. Try “Send both requests”: the release before the fix confirmed both and double-booked the teacher; this one confirms one. Your bookings stay in your own sandbox.

The run, call by call

Times are UTC. Yellow is an agent, pink is the operator role (played by the build session, see above), dark is Paperclip itself, grey is the release pipeline.

  1. 113:33

    OperatorThe requirement is written before any fix.

    A test file says a 30-minute session cannot start inside a 60-minute one and that simultaneous requests confirm at most one. On the baseline it fails 5 of its 6 cases. Red test run (recorded at 13:50, when the commit was first pushed), commit 259df74.

  2. 213:34

    OperatorTicket BOO-1 opens in Paperclip, owned by the Implementer.

    The ticket carries the repository, base commit, acceptance criteria, test command, constraints and next action. Its execution policy sends finished work to the Reviewer agent, then to the operator user for approval.

  3. 313:34

    ImplementerMoves the overlap check inside the write.

    One conditional INSERT instead of a read followed by a write, so two requests can no longer both pass. No schema change, which keeps a rollback safe. Commit 13e6509, 22 of 22 tests. It marks the ticket done; Paperclip turns that into “in review”.

  4. 413:37

    PaperclipThe handoff to review stalls.

    The Reviewer's wake-up was skipped because the Implementer's run had not yet released its workspace lease (it did, 81 milliseconds later). Nothing retried it. The ticket read “in review” while nobody worked on it.

    Noticed by the operator six minutes later, from the wake-up log, not from the board.

  5. 513:44

    OperatorWakes the Reviewer by hand.

    An unplanned intervention, recorded as one.

  6. 613:46

    ReviewerApproves, with its own evidence.

    Reran the tests, swept all 81 combinations of lengths and offsets, fired 300 rounds of 12 concurrent overlapping requests: no overlap. It left one non-blocking note. It asked for no changes, so no delivery was refused in this run.

  7. 713:49

    OperatorApproved in Paperclip by the operator account.

    After the session's own checks: tests on a fresh checkout, five race rounds against a local D1 database (one booking confirmed each time), and the same race against the old release on staging (three of three rounds double-booked). The decision comment lists what was inspected.

  8. 813:50

    PipelinePull request merged, tested, deployed to staging.

    Pull request #1, release 7e4de34. Staging smoke test passed.

  9. 913:51

    PipelineProduction waits for its own approval.

    The earlier release had been approved at 13:39; that approval covered its run only. The production job, held by the protected environment's approval gate, does not start. At 13:39 a first request had been rejected on purpose, and nothing was deployed.

  10. 1013:52

    OperatorApproved by the operator account. The fix is live.

    Release run. Five race rounds on production: one booking confirmed each time.

  11. 1113:55

    OperatorRollback to the previous release.

    Approved through the same gate. The drill bookings made before and after the fix were all still there. With the old code back, the race double-booked again, as expected.

    The first rollback attempt failed: rolling back the app had also rolled back the release scripts, including an old smoke-test bug. The workflow now takes its tooling from itself, not from the release.

  12. 1213:57

    OperatorForward to the fix again.

    Five drill bookings intact, made under the old release, the fix, and the old release again. Release run.

  13. 1313:59

    OperatorA worker is killed mid-task, on purpose.

    On a second ticket, BOO-2 (tests around the Paris clock change), the Implementer's process was killed while it was writing. Paperclip marked the run failed and retried it on its own, about 40 seconds later. The retry found the half-written file, finished it and corrected one wrong expectation. Reviewed, approved, pull request #2.

    The handoff to review stalled again, the same way, 43 milliseconds apart. Two handoffs, two stalls.

Operator decisions

7

Two approvals in Paperclip; five in the release gate, one of them a deliberate rejection.

Unplanned interventions

4

Two in Paperclip, both stalled handoffs; two in the release scripts, both caught by the pipeline or the drill.

Questions to rebuild context

0

Neither agent asked the operator anything. The ticket held what they needed.

A handoff can fail without saying so

Paperclip enforced the review and the approval stage every time, but both handoffs to the reviewer were skipped and left a ticket looking busy while idle. Watching for skipped wake-ups is part of running it.

Approval is per run, and the run is per commit

The release workflow resolves one commit, tests it and deploys only that commit after approval. Approving the old release did not let the fix through: the fix waited for its own approval.

Rollback covers code, not data

Bookings survived both directions because the fix needed no schema change. Not shown: restoring the database, undoing external side effects, or rechecking bookings taken while the old code was back.

Agents ran in a box

Paperclip and both agents ran in a container holding only this repository: no deploy key, no GitHub credentials, no access to the host machine. Commits left the box only through the operator role.

What Paperclip did, and what was done beside it

In this exercise Paperclip handled ownership, assignment, execution state, the review stage and the approval stage held by the operator user. Application correctness, deployment authorisation, smoke tests and data recovery were implemented or configured separately, in the code and in a protected GitHub environment.

The gate held the production job, not the only key: the staging job deployed on every push to main with the same account-wide Cloudflare token and no reviewer. Both deploy secrets were removed from the GitHub environments after the run (14:50 UTC); later corrections to this page and the app were deployed by the build session from its own machine.

Set up outside Paperclip and declared in the repository: the baseline app, the seeded test, the release pipeline, the container, moving commits from the container to GitHub, the pull request and the release approvals. Paperclip 2026.1012.0 (commit bba6a45), claude_local adapter on the CLI engine, Claude Code 2.1.299.

Not covered: requesting a time, payments, more than one currency, notifications. No incremental model API charges during this recorded run: the agents used an existing paid Claude Code subscription with extra usage turned off, checked before and after.
