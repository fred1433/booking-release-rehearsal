Paperclip booking-release rehearsal

Three tickets on a small booking app, run through a real Paperclip instance on 14 October 2026: agents fixed and reviewed, an operator account approved, a release gate held the production job, and a skipped handoff was recovered without anyone chasing it.

Independent demonstration using synthetic data. No access to any client's code or Paperclip instance. Payments are not connected.The operator role (Paperclip approvals, GitHub environment approvals and merges) was played by the build session through the operator account; no person reviewed these changes.

The app below is the current demo build, deployed by the build session from its own machine after the recorded run, outside the release gate. The release that went through the gate was B (app code db5931d); this build adds BOO-3 and the fixes listed in the README.

The result

  • Held

    Paperclip enforced review and approval on all three tickets. Overlapping requests confirm one booking, at the write. A lost reply retried with the same key returns the original booking.

    Try “Send both requests” in the app: one 201, one 409.

  • Gate

    The production job waited for an approval tied to its run and commit; a rejected request deployed nothing.

    Not proven: the staging job held the same account-wide deploy token without a reviewer, so not every production-capable credential was behind the gate.

  • Rollback

    A → B → A → B kept all five drill bookings. Schema-compatible, not booking-safe: with the old code back, the race double-booked again.

Every handoff to the reviewer stalled

  1. BOO-1: wake-up skipped, lease released 81 ms later. Re-woken by hand after 6 minutes.
  2. BOO-2: same, 43 ms. Re-woken by hand.
  3. BOO-3: same, 95 ms. Recovered by a reconciler running beside Paperclip: one wake-up 11 seconds after the handoff, one review run, no second reviewer. Its fallback, one blocker issue if the retry starts nothing, is unit-tested only.
  1. Requirement first. Each ticket starts from a test that fails on main.
  2. Implementation in Paperclip. The Implementer works in an isolated container and commits on a branch.
  3. Review, then approval. The Reviewer approved all three without changes; the operator user approved after its own checks.
  4. Release. Commits leave the container as a bundle; tests, staging, then production behind the gate.
  5. Rollback drill. Through the same gate, with bookings kept.

On an existing setup, the first 48 hours would preserve before changing:

  1. agree what “launched” means and who decides releases; inventory versions, open work, skipped wake-ups and the real deployment path, read-only;
  2. walk the booking journey in a test environment and rank the blockers with evidence;
  3. take one blocker through the existing flow, adding only the missing controls.

What Paperclip did, and what was built beside it

Paperclip handled ownership, assignment, execution state, the review stage and the approval stage held by the operator user. Beside it: correctness in the code, the release gate, smoke tests, the rollback drill and the handoff reconciler. Existing bookings stayed readable across every code deployment; database restore was not exercised.

This rehearsal shows hands-on work with Paperclip on a small, synthetic slice. It does not show prior operation in a real business, a measured reduction in staff supervision, or a marketplace launch.
